# 随机运行与积分回放联动设计

日期：2026-08-19

## 目标

在不改变现有导航、参数栏和整体视觉风格的前提下，完成三个改进：

1. 普通“运行仿真”每次自动产生新的随机结果，不要求用户手动修改种子。
2. 证明仿真确实执行了完整计算，展示真实工作量与耗时，不添加人为等待。
3. 让地图回放条同步驱动联盟积分、当前占领地格价值，以及单玩家战功/占领积分流水。

## 已确认范围

- 单玩家积分流水只包含战功积分和占领积分。
- 不包含任务积分、奖励价值或最终奖励事件。
- 其他 UI 不调整，地图继续作为主视觉。
- 图表保持轻量，只承担辅助分析作用，不新增独立的重型分析页面。
- 批量实验沿用确定性连续种子；普通单局运行默认随机。

## 现状与根因

当前引擎是确定性仿真：相同参数、人口与种子会产生完全相同的结果。页面的“运行仿真”直接复用草稿中的 `config.seed`，所以只要用户不修改种子，重复点击就会得到同一局。

默认一局把 48 小时压缩为 10 秒一个时间步进行计算。基准局实际执行 17,280 个时间步、27,039 次出征、20,521 次战斗、1,199 次占领和 48,764 条时间线事件，核心计算约 1.5 秒。快速得到结果来自时间压缩与本地同步计算，不代表没有执行仿真。

## 方案比较

### 方案 A：只把种子递增

每次运行使用 `seed + 1`。实现简单，但结果序列可预测，用户连续打开页面仍从同一默认序列开始，不能满足“每次都是随机新局”的直觉。

### 方案 B：随机单局 + 明确复现入口（采用）

普通运行使用浏览器安全随机源生成新的 32 位正整数种子；页面显示本局种子，并提供次要操作“按当前种子复现”。随机探索和问题复现都能兼顾。

### 方案 C：完全移除种子

界面最简单，但失去复现异常战局、对比参数和自动化校准的能力，不适合数值分析工具。

## 随机运行设计

### 普通运行

1. 用户修改除种子外的参数。
2. 点击“运行仿真”。
3. 页面生成新的非零 32 位种子，并同时用于人口生成、联盟匹配、策略分配和战斗引擎。
4. 完成后，草稿与已应用配置都更新为该种子，避免页面显示与结果不一致。
5. 连续运行时保证不会复用紧邻上一局的种子；若随机源碰撞则重新生成。

### 复现运行

- 在现有运行按钮旁增加低强调的“按当前种子复现”。
- 复现使用参数面板中的种子，不生成新值。
- 相同参数和种子必须产生完全相同的玩家、地图回放、排名与积分事件。

### 批量实验

- 批量实验继续使用“基准种子 + 序号”的确定性序列。
- 当普通单局生成新种子后，该种子成为下一次批量实验的基准种子。

## 真实计算证据

不故意延长运行时间。每次运行完成后，从真实结果派生并轻量展示：

- 模拟时间步数量；
- 时间线事件总数；
- 出征次数；
- 战斗次数；
- 占领次数；
- 浏览器实际计算耗时。

运行中沿用“仿真运行中”状态，完成后在地图回放标题或底部信息区显示一行计算摘要。耗时只用于用户理解性能，不参与仿真结果，不写入可复现结果对象。

## 积分事件模型

新增紧凑的 `PlayerScoreEvent`：

```ts
interface PlayerScoreEvent {
  second: number;
  playerId: string;
  allianceId: 1 | 2 | 3;
  source: "battle" | "occupation";
  delta: number;
  totalAfter: number;
  tileId: number;
  kills?: number;
  cumulativeKills?: number;
  tileType?: "normal" | "resource" | "core";
}
```

### 战功事件

- 玩家累计击杀跨过 `killsPerPoint` 的整数档位时产生事件。
- 一次战斗即使增加多点战功，也只记录一条事件，例如“击杀 120,000，战功 +12”。
- 未跨过积分档位的战斗不产生积分事件。

### 占领事件

- 占领完成并实际获得占领积分时产生一条事件。
- 事件记录地格、地格类型、本次积分和该玩家累计积分。

### 数据规模

事件数量上限接近“发生积分变化的战斗次数 + 占领次数”，而不是按每一点积分拆分。默认局预计为数万条以内。结果中按玩家建立索引或在分析层缓存索引，界面只渲染当前玩家在当前回放时刻之前的有限条目，避免一次绘制全量事件。

## 回放快照积分

每个整点快照增加三方累计积分数据：

- 战功累计；
- 占领积分累计；
- 两者之和。

占领地格价值继续使用快照中按当前归属计算的地图分。这样可明确区分：

- “当前占领价值”：这一时刻地图上仍被持有的地格价值；
- “累计积分”：截至这一时刻已经获得的战功与占领贡献。

## 界面设计

### 仿真总览

- 保留现有地图卡片、尺寸和回放进度条。
- 地图仍是主要视觉区域。
- 在地图旁现有辅助区域增加三方当前累计积分和小型趋势线。
- 图表使用细线、低对比网格和紧凑高度，不新增顶部大指标卡阵列。
- 地图上只保留原有地格表现；当前争夺状态使用现有描边/队列表现，不添加大面积图表式覆盖。
- 拖动回放条时，同步更新地图、当前占领价值、三方累计积分和趋势游标。

### 玩家与联盟排名

- 排名表保持原样。
- 点击玩家行后打开或更新玩家详情区域。
- 详情显示战功、占领积分、总积分，以及按时间倒序排列的积分流水。
- 流水受全局回放时间约束，只显示当前时刻之前已经发生的事件。
- 默认只渲染最近一段事件，并提供继续加载，避免大量 DOM 节点。

## 数据流

1. 页面选择随机运行或种子复现。
2. 人口生成与引擎共享同一个实际种子。
3. 引擎在战斗和占领结算点写入积分事件，并在整点生成累计积分快照。
4. 页面保存运行结果和实际耗时。
5. 回放时间是地图、积分辅助图表和玩家流水的唯一时间源。
6. 所有视图从同一个结果对象读取数据，不进行第二次随机计算。

## 错误与边界处理

- 随机源不可用时使用时间、高精度计时与递增计数混合生成非零种子。
- 新种子与上一局重复时重新生成。
- 没有积分事件的玩家显示空状态。
- 回放时间为 0 时所有累计积分为 0。
- 同一秒发生多条事件时保持引擎处理顺序，确保 `totalAfter` 单调一致。
- 修改参数但未运行时，地图、积分和流水继续展示已应用结果。

## 测试策略

### 随机与复现

- 连续普通运行使用不同种子并产生不同结果。
- 随机种子同时传入人口和战斗引擎。
- 按当前种子复现得到完全相同结果。
- 草稿与已应用种子在运行后保持一致。

### 引擎积分事件

- 9,999 击杀不产生战功事件；10,000 产生 `+1`。
- 单次跨越多个档位只产生一条聚合事件。
- 普通、资源、核心地格占领生成正确积分事件。
- 每名玩家事件的累计值与最终战功、占领积分一致。
- 相同种子的积分事件顺序完全一致。

### 回放联动

- 不同小时快照返回对应的三方累计积分与当前占领价值。
- 拖动时间轴更新辅助趋势游标和数值。
- 玩家详情只显示回放时刻之前的积分事件。
- 地图仍是总览中的主要区域，辅助图表不创建新的主导航页面。

### 计算证据

- 摘要中的出征、战斗、占领和事件数来自实际时间线。
- 计算耗时为非负值，但测试不依赖具体性能数值。

## 非目标

- 不模拟真实时间播放 48 小时战局。
- 不通过固定延迟伪造进度。
- 不记录任务、奖励价值或奖励领取流水。
- 不重做导航、参数面板、地图视觉和整体设计语言。
- 本轮不改变既有战斗、行动力、占领、士气或积分公式。
